**Bottom line up front:** Per-kill/per-round timelines for 2023–2026 are **gone and unrecoverable** — Riot serves ~100 matches deep. But **per-match ground truth (match UUID, UTC start, UTC end, mode, win/loss) for his entire account back to 2020 IS recoverable today**, free, via a Riot GDPR data request (~30 day turnaround). And his mp4s already carry a true-UTC timestamp he is currently discarding. ## OFFICIAL-RIOT-API

**Endpoints that exist (verified live on the portal, 2026-09-13)** — https://developer.riotgames.com/apis lists exactly six VALORANT APIs: `val-console-match-v1`, `val-console-ranked-v1`, `val-content-v1`, `val-match-v1`, `val-ranked-v1`, `val-status-v1`.

`val-match-v1` (https://developer.riotgames.com/api-details/val-match-v1):
- `GET /val/match/v1/matches/{matchId}`
- `GET /val/match/v1/matchlists/by-puuid/{puuid}`
- `GET /val/match/v1/recent-matches/by-queue/{queue}` — queues: competitive, unrated, spikerush, tournamentmode, deathmatch, onefa, ggteam, hurm, swiftplay, skirmish2v2, skirmishascension1v1, skirmishascension2v2. Returns only matches completed **in the last 10 minutes** (12h for esports routing). Useless here.

**The match detail payload is exactly what would solve the CV problem.** `MatchDto` → `roundResults[]` (`RoundResultDto`) contains kill events with `timeSinceGameStartMillis` and `timeSinceRoundStartMillis`, victim locations, assists, per-shot damage (head/body/leg), per-round economy, and ability usage. That is millisecond-accurate kill labeling. The data model is not the problem; **access and retention are.**

**Access — this is a hard blocker.** Personal and development keys **cannot touch the VALORANT API at all**, and Riot has restated this repeatedly:
- https://www.riotgames.com/en/DevRel/valorant-api-launch (2020-07-09): *"Personal keys and developer keys do not have access to the VALORANT API… you won't be able to get responses from your non-production keys. This is on purpose."*
- Riot staff `RiotTuxedo` (COLLABORATOR), https://github.com/RiotGames/developer-relations/issues/560, 2021-10-07: *"We require any VALORANT match history calls to first verify the player who owns their account is fine with making their match history public via RSO. We're not going to generate RSO clients for every personal key and we're not going to build a mechanism to associate a key with an individual account… this request is unlikely to happen."* Issue closed 2023-01-15, never implemented.
- Riot DevRel support, still current: *"Personal key applications requesting VALORANT access will not be approved."* RSO access is gated behind a production key. Production applications reviewed weekly, *"sometimes… up to three weeks."*

So the path is: apply for a **production key** (a pitch/review process, discretionary), then get invited to **RSO** integration, then build an OAuth flow to authorize his own account. For a solo personal project with no public product, approval is unlikely — Riot's stated policy bars "personal profiles"/scouting tools without opt-in and bars products that substitute for matchmaking.

**Rate limits** (dev vs production, per region): development 20 req/1s and 100 req/2min; production 500 req/10s and 30,000 req/10min. Moot for VALORANT since dev keys get 403.

**Retention:** the 2019 announcement of a 2-year match-history retention window (https://www.riotgames.com/en/DevRel/match-history-retention-Change, effective 2019-08-07, timeline data 1 year) predates VALORANT and does **not** describe VALORANT behavior. See HISTORICAL-JOIN-FEASIBILITY for the real number.

## COMMUNITY-APIS

### HenrikDev — api.henrikdev.xyz (v4.5.0, docs "Last Updated: 18.12.2025")
**Live-probed 2026-09-13:** `GET https://api.henrikdev.xyz/valorant/v1/status/na` → **HTTP 401 `{"errors":[{"code":0,"message":"Unauthorized",...}]}`**. An API key is now mandatory on every endpoint, including trivial ones.

This is the practical way to get Riot-grade data **without** a production key or RSO — it proxies the in-game (pvp.net) API using Henrik's own infrastructure, keyed by Riot ID or PUUID, no credentials from the user.

Endpoints that matter:
- `GET /valorant/v4/by-puuid/matches/{affinity}/{platform}/{puuid}?size=&start=&mode=&map=`
- `GET /valorant/v4/match/{affinity}/{match_id}` — arbitrary match UUID
- `GET /valorant/v1/by-puuid/stored-matches/{affinity}/{puuid}?mode=&map=&size=&page=`

**The v4 payload carries exactly the labels needed.** Verified from the live OpenAPI spec (https://api.henrikdev.xyz/openapi.json, fetched 2026-09-13, 147,238 bytes). `MatchesV4Data` requires `metadata, players, observers, coaches, teams, rounds, kills`. `MatchesV4DataKill` requires:
```
time_in_round_in_ms, time_in_match_in_ms, round, killer, victim,
assistants, location, weapon, secondary_fire_mode, player_locations
```
`MatchesV4DataRound`: `id, result, ceremony, winning_team, stats`, plus nullable `plant`/`defuse`. `MatchesV4DataMetadata`: `match_id, map, game_version, game_length_in_ms, started_at, is_completed, queue, season, platform`.

That is a per-kill timeline with millisecond offsets, weapon, and 3D positions for all ten players at each kill. Everything valclips' OpenCV analyzer is trying to guess.

**Rate limits** (https://github.com/Henrik-3/unofficial-valorant-api, README v4.5.0): Basic **30 req/min** (instant, Discord join required), Enhanced **90 req/min** (apply, 1–2 week answer), Production/Custom (Patreon level 4/5 required for high limits or paid products). Since v4.0.0 the meter counts **1 per API call + 1 per background Riot call**, so `?size=10` on a cold cache costs ~5, warm cache costs 1.

**Policy — read this before building.** Henrik's README explicitly disallows: *"Big analytic projects — Why? Because of data privacy. Rito set RSO as a requirement for their official API…"*, public store checkers, and ToS-breaking use. A personal tool labeling his own clips is within bounds; a public "AI Valorant highlight platform" is not.

**"Stored matches" is not an archive.** https://docs.henrikdev.xyz/valorant/guides/stored-matches.md is explicit: *"Stored matches are an accumulating materialized subset of Riot's match history, not a pre-populated mirror of every match."* It seeds from Riot's competitive-updates history, and a match may be absent because it *"was simply never requested by any developer using this API."* Also: *"`total` is not the player's total number of matches."* This does **not** solve 2023.

## LOCAL-CLIENT-API

**There is no VALORANT equivalent of League's Live Client Data API on port 2999.** Riot deliberately does not expose live gameplay state locally — that is anti-cheat surface. Confirmed by absence across all endpoint catalogs (valapidocs.techchrism.me's "Local Endpoints" section, the HeyM1ke and nycodeghg/techchrism reverse-engineering repos).

**What the local API actually gives you:**
- Lockfile at `%LOCALAPPDATA%\Riot Games\Riot Client\Config\lockfile`, single line `name:pid:port:password:protocol`. Auth = `Authorization: Basic base64("riot:"+password)` against `https://127.0.0.1:{port}` (self-signed cert).
- `GET /entitlements/v1/token` — the bearer + entitlements JWT that unlock the remote pvp.net endpoints.
- `GET /chat/v4/presences` — your own and friends' presence. The `private` field is a base64 JSON blob described by the docs as containing *"useful information such as party and in-progress game score."* In practice this surfaces session loop state (menus/pregame/ingame), party state, queue id, and the running round score.
- `WSS wss://127.0.0.1:{port}` with the same Basic auth — subscribe to named events (the standard tooling is techchrism's "Valorant WebSocket Logger" via the Local Help endpoint).
- Current-game endpoints (`glz`/`pd`) give the live match ID and roster mid-match.

**Verdict for live labeling: the Riot local API alone is NOT sufficient.** It gives you match boundaries, match ID, and round score — enough to segment a session into matches and rounds in real time, which is genuinely useful. It does **not** emit kill events.

**The thing that does emit kill events is Overwolf GEP** (https://dev.overwolf.com/ow-native/live-game-data-gep/supported-games/valorant/ and https://overwolf.github.io/api/games/events/valorant). Features: `gep_internal`, `me` (name, ID, region, agent, health, abilities, server), `game_info` (scene/state), `match_info` (round/match, roster, scoreboard, kill feed, map, spike status), `kill`, `death`. Events: `match_start`, `match_end`, `spike_defused`, `spike_detonated`, `kill_feed`, `shop`, `scoreboard_screen`, `planted_location`; `kill`, `assist`, `headshot`; `death`. `kill_feed` payload carries attacker/victim names, weapon, headshot flag, up to 4 assists, ultimate ability name, teammate flags.

Documented limitations: **events carry no timestamps** (you stamp them on arrival — fine, you're recording in real time anyway), `match_end` doesn't fire in custom/training, players with stream mode on appear as agent names, roster unsupported in Escalation, shop unsupported in TDM, `kill_feed` unsupported in TTM. Overwolf also generates its own match IDs independently of Riot's, so you must join back to a Riot match ID via the local API or a post-match lookup.

**So the going-forward recipe is: NVIDIA App keeps recording as-is + an Overwolf app (or a local-API poller) writes a JSONL event log with wall-clock timestamps + join on UTC.** That yields perfectly labeled training data with zero CV, forever. This is the single highest-leverage build.

## HISTORICAL-JOIN-FEASIBILITY — **definitive verdict**

### Per-kill / per-round timelines for 2023–2026: **NO. Definitively not obtainable.**

The authoritative source is Riot DevRel closing https://github.com/RiotGames/developer-relations/issues/426 ("[BUG?] Valorant matchlist resets once in a while") on **2023-12-27** with the label **`closed: is working`** (i.e. working as intended) and the comment (permalink https://github.com/RiotGames/developer-relations/issues/426#issuecomment-1869833459, author `tisbells`, repo CONTRIBUTOR):

> **"Closing old issues - VAL match history is limited to roughly the last 100 matches."**

Independently corroborated by https://github.com/RiotGames/developer-relations/issues/815 (opened 2023-09-11, **still open**, labels `scope: val`, `api: val-match-v1`, `pending: acknowledged`): three accounts with >100 matches in the prior two months got **85, 85 and 95** match IDs back, with earliest dates of 2023-08-29, 2023-08-17 and 2023-07-23 — i.e. roughly a **2-month sliding window** for an active player. Riot has not changed this in the ~3 years since.

This is a hard cap, not a rate limit, not a pagination bug. Every downstream API — official, HenrikDev, tracker, op.gg — reads through that same window. **Kill timestamps for a clip recorded in 2023, 2024, 2025, or even early 2026 do not exist on any server he can reach.**

Two corollaries worth stating plainly:
- **The VALORANT Replay System does not rescue this.** Replays shipped 2025-09-16 (PC, patch 11.06), 2025-10-09 (China, 11.07b), 2025-11-11 (console, 11.10), and cover Competitive/Unrated/Swiftplay/Premier (customs added in 12.00). But **replays are wiped at the end of each patch (~2 weeks)**. No retroactive value, and no export path.
- **Riot's 2019 "2-year retention" announcement is a red herring** — it's a League-era policy and is far more generous than VALORANT's actual ~100-match behavior.

### Per-MATCH ground truth for 2020–2026: **YES. Obtainable today. This is the finding that changes the project.**

Riot's GDPR/CCPA personal data request returns a `data.zip` containing **`data/valorant_match_history.json`**. Verified schema (from a real dump published at https://github.com/moalhaddar/valorant-data-analyzer):

```json

  "game_start_time_utc": "2020-06-16 23:41:03",
  "game_end_time_utc":   "2020-07-17 00:09:35",
  "game_id":             "05766ec6-20a1-46c2-87ec-e6f08e925197",
  "game_mode":           "Matchmaking",
  "game_type":           "Unrated",
  "game_outcome":        "Loss",
  "realm_id":            "eu"

```

That repo's README shows its author's dump covering **2020-06-16 → 2020-12-27, 2,215 games** across Unrated / Spike Rush / Ranked / Deathmatch / Snowball / Custom — i.e. **the player's complete history back to VALORANT's launch month**, not a 100-match window. The fields are already UTC and already contain both start *and* end, so the clip join is a containment test, not a nearest-neighbor guess.

**How to request:** support ticket at https://support-valorant.riotgames.com/hc/en-us/requests/new → request type **"Account Management, Data Requests, or Deletion"** → **"Formal Personal Data Request"**. **30-day** waiting period. Free. Covers all Riot titles on the account. Riot's current article is https://support-valorant.riotgames.com/hc/en-us/articles/31857321662995-Requesting-Your-Account-Data (JS-rendered; I could not extract its body — see open questions).

**Recommendation: file this request today.** It is free, costs him ten minutes, has a 30-day clock, and blocks nothing else. Every week he delays is a week the rest of the project can't use the labels.

### What the join actually looks like

```
clip_end_utc   = ffprobe format_tags=creation_time        # already UTC, verified below
clip_start_utc = clip_end_utc - format.duration
match          = the row where game_start_time_utc <= clip_end_utc <= game_end_time_utc
```
Matches never overlap for a single player, so the join is unambiguous. Clips that fall in no interval are menus/warmup/custom-lobby noise — which is itself a useful negative label, and lets him drop non-gameplay footage without touching a pixel.

## TOS-AND-BAN-RISK

Riot ToS §7.1 (https://www.riotgames.com/en/terms-of-service) prohibits, among User Rules:
- item 11 — *"Using any unauthorized third party programs, including mods, hacks, cheats, scripts, bots, trainers and automation programs that interact with the Riot Services in any way"*, and *"unauthorized third party programs that collect info about the Riot Services by reading areas of memory used by the Riot Services to store info"*

- item 12 — *"Accessing or attempting to access areas of the Riot Services that are not made available to the public"*

Penalties listed: temporary bans, suspension/termination, **hardware bans**.

> *"Overlays and internal tools using the API, game client, and in-game APIs should continue to function… External tools reading memory will no longer work, and you'll need to change methods."*
> *"There is absolutely no allow list for Vanguard."*

## SHADOWPLAY-METADATA

Everything in this section was **verified by direct measurement on six of his actual clips** in `~/Documents/` (`Valorant 2024.12.17 - 20.27.17.04.DVR.mp4` and five from 2026-08), not from documentation.

### 1. The mp4 carries a true-UTC timestamp — and the repo throws it away

```
$ ffprobe -v quiet -show_entries format_tags=creation_time -of default=nw=1:nk=1 <file>
2026-08-18T01:05:58.000000Z
```
Format tags present: `major_brand=mp42`, `minor_version=0`, `compatible_brands=isommp42`, `creation_time`, `date=2026`. Stream 0 = h264 1920x1080 @ 60000/1001, streams 1 and 2 = AAC named **"System sounds"** and **"Microphone"** (NVIDIA's separate-audio-tracks feature — he can mute his own mic or isolate game audio without re-encoding).

`creation_time` **equals the filesystem mtime to within ≤1s on 5 of 6 files** (the 6th differs by 1s). Since NTFS mtime is stored in UTC and survived the SMB copy, this independently confirms `creation_time` is genuine UTC, not a local-time value mislabeled as Z. **This is the join key.**

### 2. The filename timestamp is in US Central, is DST-dependent, and is NOT UTC

`creation_time_utc − filename_timestamp`, measured:

| file | delta |
|---|---|
| `Valorant 2024.12.17 - 20.27.17.04.DVR.mp4` | **6h 1s** |
| `Valorant 2026.08.10 - 00.01.58.03.DVR.mp4` | **5h 2s** |
| `Valorant 2026.08.12 - 21.34.58.02.DVR.mp4` | **5h 5s** |
| `Valorant 2026.08.17 - 18.17.53.02.DVR.mp4` | **5h 1s** |
| `Valorant 2026.08.17 - 19.51.50.03.DVR.mp4` | **5h 1s** |
| `Valorant 2026.08.17 - 20.05.57.04.DVR.mp4` | **5h 1s** |

UTC−6 in December, UTC−5 in August = **America/Chicago (CST/CDT)**. A fixed offset would be wrong in half the year; the DST-varying delta rules out any constant-offset fix. **Naively parsing the filename and calling it UTC is off by 5 or 6 hours depending on the date** — which would silently join every clip to the wrong match, or to none.

**Concrete bug in the existing repo:** `~/Documents/GitHub/valorant-clips/src/valclips/parser.py:23` and `:37` build a **naive** `datetime(...)` from the filename and store it as `recorded_at`; `~/Documents/GitHub/valorant-clips/src/valclips/db.py:16` persists it as untyped `TEXT`. Meanwhile `~/Documents/GitHub/valorant-clips/src/valclips/scanner.py:64-100` (`_extract_metadata`) pulls `duration`, `bit_rate`, `width`, `height`, `codec_name`, `r_frame_rate` from the ffprobe JSON — and **never reads `format.tags.creation_time`, even though it is already sitting in the `probe` dict it has in hand.** The fix is about three lines and no re-scan of the network shares beyond what `scan` already does. Do this before anything else; every downstream join depends on it.

Caveat: America/Chicago is what *these six files* say. If the capture PC's timezone ever changed across 2023–2026, the filename offset changes with it. **Derive nothing from the filename — read `creation_time` per file.**

### 3. The timestamp is the END of the clip, not the start

The deltas above are 1–5s, not ~80s, so the filename instant and `creation_time` mark the same moment. Independently confirmed by third-party testing at https://github.com/mifi/lossless-cut/issues/1017 (2022-02-07):

> *"For shadowplay instant replay feature… an mp4 file is produced with the file modified time, file created time, and all the clip metadata times… equal to the time that the clip ended at."*

So `clip_start_utc = creation_time − duration`. Durations measured: 74.26s, 80.04s, 80.10s, 80.42s, 80.46s, 97.77s. Getting this backwards would shift every clip ~80s into the wrong round.

### 4. The game name IS embedded — ffprobe just doesn't show it

`ffprobe` does **not** surface it. It lives in an undocumented `moov/udta/Xtra` box (a Windows Media `Xtra` atom). I parsed it directly:

```
WM/EncodedBy            = "NVIDIA APP"        (2026 files)
                        = "GeForce SHARE"     (2024 file)
WM/UniqueFileIdentifier = {"Source":"NVIDIA APP","Codec":"H264","B64":"<base64>"}
```
base64-decoded, identical across all six files except the trailing field:
```json
{"DRSAppName":"valorant-win64-shipping.exe","DRSProfileName":"Valorant",
 "ShortName":"valorant","CmsId":101529211,"MediaType":"InstantReplay"}
```
The 2024 (GeForce SHARE-era) file has the same four fields but **no `MediaType`** — so `MediaType` was added by the NVIDIA App rewrite and is only present on newer captures.

Practical value: an authoritative game-ID that does not depend on the filename containing the word "Valorant" (`~/Documents/GitHub/valorant-clips/src/valclips/parser.py:64` `is_valorant_clip()` currently relies purely on the filename string, which will miss every renamed or manually-titled clip in the `all_mp4` directories — and `config.py` lists seven such directories). It also distinguishes Instant Replay from manual recordings on post-2025 files, which matters because manual recordings can be arbitrarily long and their timestamp semantics differ (per the lossless-cut report, manual ShadowPlay recordings set file *created* time to the clip **start**).

Neither `exiftool` nor `mediainfo` is installed on this Mac; a ~40-line pure-Python box walker is sufficient and has no dependencies. I have a working one at `/tmp/nvmeta.py`.

### 5. Scale
Measured bitrate 76,284,898 bps (1080p60 H.264) on a 763,796,186-byte / 80.1s file. At that bitrate, **10 TB ≈ 320 hours ≈ 13.3 days of continuous footage**, or ~14,400 clips at 80s each. (The repo's CLAUDE.md says ~2,800 clips indexed ≈ 2.1 TB, so either the 10TB figure includes non-Valorant/manual recordings or the scan never reached the full corpus — worth reconciling.)

- Riot API rate limits: development/personal key = 20 req/1s and 100 req/2min per region; production key = 500 req/10s and 30,000 req/10min per region.

- HenrikDev's stored-matches guide states 'Stored matches are an accumulating materialized subset of Riot's match history, not a pre-populated mirror of every match' and that a match may be absent because it 'was simply never requested by any developer using this API' — so it is not a retroactive archive.
- HenrikDev exposes GET /valorant/v4/match/{affinity}/{match_id} accepting an arbitrary match UUID, making a batch probe of exported game_ids a viable (low-hit-rate) recovery path.
- Probed live 2026-09-13, no auth, all HTTP 200: valorant-api.com /v1/agents=29 playable, /v1/maps=26, /v1/weapons=20, /v1/gamemodes=17, /v1/seasons=53, /v1/competitivetiers=5; /v1/version reports release-13.05, build 13.05.00.5350494, buildDate 2026-08-20T23:51:14Z.
- valorant-api.com serves per-agent `killfeedPortrait` and `minimapPortrait` images and per-weapon `killStreamIcon` images (e.g. https://media.valorant-api.com/weapons/9c82e19d-4575-0200-1a81-3eacf00cf872/killstreamicon.png for Vandal) — the exact sprites the game composites into the kill feed, usable directly as CV templates.

- VALORANT has no equivalent of League's Live Client Data API on port 2999; the local Riot Client API (lockfile at %LOCALAPPDATA%\Riot Games\Riot Client\Config\lockfile, format name:pid:port:password:protocol, Basic auth as riot:{password}) exposes entitlements token, presence, session state and a local WSS event stream — but no kill events.
- Overwolf GEP for VALORANT does emit real-time kill data: features gep_internal/me/game_info/match_info/kill/death, events match_start, match_end, spike_defused, spike_detonated, kill_feed, shop, scoreboard_screen, planted_location, kill, assist, headshot, death; kill_feed carries attacker/victim, weapon, headshot flag, up to 4 assists and ultimate name.

- Measured on Sohum's own clip ~/Documents/Valorant 2026.08.17 - 20.05.57.04.DVR.mp4: ffprobe format_tags=creation_time returns 2026-08-18T01:05:58.000000Z, which equals the filesystem mtime to within 1s, confirming creation_time is genuine UTC rather than mislabeled local time.
- Across six of his real clips, creation_time_utc minus the filename timestamp is exactly 6h+1s for the December 2024 file and 5h+1..5s for the five August 2026 files — UTC-6 in winter and UTC-5 in summer, which identifies the capture PC's timezone as America/Chicago (CST/CDT) and rules out any fixed-offset correction.

Independently corroborated by https://github.com/mifi/lossless-cut/issues/1017 (2022-02-07): for ShadowPlay instant replay 'the file modified time, file created time, and all the clip metadata times… are equal to the time that the clip ended at.'
- Every clip embeds an undocumented moov/udta/Xtra box (not surfaced by ffprobe) containing WM/EncodedBy and WM/UniqueFileIdentifier; the base64 payload decodes to {"DRSAppName":"valorant-win64-shipping.exe","DRSProfileName":"Valorant","ShortName":"valorant","CmsId":101529211,"MediaType":"InstantReplay"}.
- WM/EncodedBy is 'GeForce SHARE' on the 2024 clip and 'NVIDIA APP' on the 2026 clips, and the MediaType field is present only on the NVIDIA App-era files — so capture-era is detectable from the container itself.
- ShadowPlay writes three streams: h264 1920x1080 @ 60000/1001 plus two AAC tracks tagged 'System sounds' and 'Microphone', so game audio and mic can be separated without re-encoding.
- Measured bitrate is 76,284,898 bps (763,796,186 bytes for 80.1s), so 10 TB is approximately 320 hours / 13.3 days of footage, or ~14,400 clips at 80s each — against the ~2,800 clips the repo's CLAUDE.md says are indexed (~2.1 TB).
