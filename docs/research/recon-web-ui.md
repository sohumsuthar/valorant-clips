## STREAMING-PROXY

`stream_clip`, routes.py:252-311. Reads `clip.file_path` from SQLite, `open(file_path,"rb")`, `seek(start)`, yields 1 MB chunks via `StreamingResponse`. Range parsing is routes.py:270-276:

```python
range_spec = range_header.replace("bytes=", "").strip()
parts = range_spec.split("-")
start = int(parts[0]) if parts[0] else 0
end = int(parts[1]) if parts[1] else file_size - 1
end = min(end, file_size - 1)
length = end - start + 1
```

I exercised this against a real 26,211-byte MP4 through the working (0.38.6) server. **Measured results — 5 real bugs:**

| Request | Expected | **Actual** |
|---|---|---|
| `bytes=0-99` | 206, `0-99/26211` | ✅ 206, 100 bytes |
| `bytes=1000-` | 206, `1000-26210` | ✅ 206, 25211 bytes |
| **`bytes=-500`** | 206, **last** 500 bytes (`25711-26210`) | ❌ **206, `Content-Range: bytes 0-500/26211`, first 501 bytes — wrong data, silently** |
| **`bytes=26211-`** | **416** | ❌ 206, `Content-Range: bytes 26211-26210/26211`, `Content-Length: 0` |
| **`bytes=99999-`** | **416** | ❌ 206, `Content-Range: bytes 99999-26210/26211`, length computes to **-73788**, Content-Length header dropped |
| **`bytes=0-99,200-299`** | 206 multipart or 200 | ❌ **HTTP 500** (`int("99,200")` → ValueError) |
| **`bytes=abc-def`** | ignore → 200, or 416 | ❌ **HTTP 500** |
| **`items=0-10`** | ignore → 200 | ❌ **HTTP 500** (naive `.replace("bytes=","")` doesn't strip a foreign unit) |
| `bytes=200-100` | 416 | ❌ 206, `Content-Range: bytes 200-100/26211`, 0 bytes |
| `bytes=0-999999` | clamp | ✅ 206, full file |

The two that will actually bite Sohum:
1. **Suffix ranges return wrong bytes with a 206 and a plausible-looking `Content-Range`.** Players use `bytes=-N` to read the MP4 `moov` atom when it is at the end of the file — which is exactly where ShadowPlay/DVR recordings put it unless `+faststart` was applied. The player gets the file *header* instead, labeled as the tail. Symptom: video that won't load or won't seek, with no server error to debug.
2. **Malformed/multi-range → 500.** Safari issues multi-range requests for media. Any such client gets a hard 500.

**Missing cache validators.** Measured response headers on a 206: `content-range`, `accept-ranges`, `content-length`, `content-type` — and nothing else. **No `ETag`, no `Last-Modified`, no `Cache-Control`.** By contrast the `StaticFiles` mount does emit both (`etag: "fae918..."`, `last-modified: ...`). So every seek in a video re-pulls bytes from the SMB share with no possibility of browser revalidation. Using Starlette's own `FileResponse` would fix the Range bugs *and* the validators in one move.

**Network-share behavior.** Per request the handler does `file_path.exists()` (routes.py:261) then `.stat()` (routes.py:264) — two extra round-trips to the share before a single byte moves. The route is `def` (not `async def`), so FastAPI runs it in the anyio worker threadpool (40 threads by default) and `StreamingResponse` iterates the sync generator via `iterate_in_threadpool`, so the event loop is *not* blocked by streaming. However, on a hung or disconnected SMB/GVFS mount those `exists()`/`stat()` calls block uninterruptibly; ~40 concurrent requests against a dead mount exhaust the threadpool and the whole app stops serving. Relevant here because the orchestrator notes `truenas-scale` is offline and `chaos.local` does not resolve. (Structural — I did not reproduce a hung mount.)

**Separate, confirmed event-loop bug:** `api_analyze_clip` (routes.py:157) is declared `async def` but calls blocking code with no `await` and no threadpool hop — `get_clip_highlights` → `subprocess.run` (highlights.py:51) and `GeminiAnalyzer.analyze` → `httpx.Client(timeout=90.0).post` (gemini_analyzer.py:224-225). FastAPI runs `async def` endpoints directly on the event loop, so **one analyze request freezes the entire server for up to 90+ seconds.** Fix: drop the `async`.

**OFFSET pagination is a non-issue at this scale — do not spend time on keyset pagination.** The actual problems:

1. **`get_sessions` is the one real query bottleneck.** db.py:555-560 selects **every** non-duplicate row with no LIMIT, materializes it in Python, and runs an O(n) `datetime.fromisoformat` pass on every single request. 587 ms at 100k, uncached, hit by both `/sessions` and `/api/sessions` — and `/sessions` then throws away all but 100 (routes.py:242). Push the gap detection into SQL (`LAG()` window function) or cache it.

2. **`get_stats` (97 ms) runs on every load of `/`**, which is the page that opens the app. Four unindexed aggregate scans (db.py:383-408).

3. **No virtualization, and none needed** — `renderClips` caps at `limit: 24` (app.js:65) into a CSS grid (style.css:292). 24 DOM nodes per page. `loading="lazy"` is on the template `<img>` (index.html:147) and survives `cloneNode`. This part is fine.

4. **Pagination is unusable at 100k.** 100,000 / 24 = **4,167 pages**, and `renderPagination` (app.js:188-194) renders only a ±3 window plus `<`/`>`. **No jump-to-page, no last-page, no total count shown.** Reaching the middle of the library is impossible without ~2,000 clicks.

5. **No URL state at all — the single worst UX gap.** All 15 filter values are module-level `let`s in app.js:4-19. Nothing is written to `location.search`, nothing is read back. Consequences: refresh loses everything; **no filtered view can be bookmarked or shared**; browser Back/Forward do not move through pages or filters; the `/` keyboard shortcut and arrow-key paging (app.js:590-610) leave no trace. For a 10TB archive where finding a clip *is* the product, this is disqualifying.

6. **Search is `LIKE '%term%'` on 3 columns + a tag subquery** (db.py:331-336) — unindexable by construction, 47 ms per keystroke after a 300 ms debounce (app.js:205-209). 7. **`img.src = ''` for thumbnail-less clips** (app.js:114). Per the HTML spec an empty `src` resolves to the *document URL*, so every thumbnail-less card fires a spurious full request for the current page — up to 24 extra hits per page load, each currently a 500. 11. **Pico CSS is loaded from `cdn.jsdelivr.net`** (base.html:7). A LAN/offline server renders unstyled.
